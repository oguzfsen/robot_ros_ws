GNSS serial usage summary
=========================

Scope
- This note ignores ROS and telemetry bridge details.
- It summarizes only the GNSS receiver behavior that can be reimplemented in a plain serial program.
- Source of truth: `src/istasyon_core/istasyon_core/gnss_base_node.py`, `src/istasyon_core/istasyon_core/ubx.py`, `message to robot codex.txt`, and current YAML config.

System model
- There are 2 u-blox/HERE4-class devices:
  1. Station/base receiver
  2. Rover receiver
- The station receiver is forced into known-fixed base mode.
- The station receiver itself generates RTCM3 corrections.
- The rover receiver itself consumes RTCM3 corrections and solves RTK internally.
- The host program does not compute RTK math. Its GNSS job is:
  1. configure the station receiver with UBX
  2. read raw RTCM bytes from the station serial stream
  3. forward those raw RTCM bytes to the rover serial stream with low latency
  4. optionally read diagnostics/position output from each receiver

Current station serial settings
- Port in current YAML: `/dev/serial/by-id/usb-u-blox_AG_-_www.u-blox.com_u-blox_GNSS_receiver-if00`
- Baudrate: `460800`
- Serial timeout: `0.2 s`
- Reconnect delay on failure: `2.0 s`
- Current mode: known-fixed base
- Survey-in is explicitly not wanted.

Current fixed base coordinates
- Latitude: `38.624275938`
- Longitude: `27.045235242`
- Altitude: `12.0284 m`
- Current YAML `position_accuracy_m`: `2.675`
- Code default `position_accuracy_m`: `0.02`
- For actual behavior, YAML wins over the code default when that YAML is used.

Important protocol fact
- The station receiver uses a single mixed serial stream.
- The same USB serial port carries:
  - outbound UBX commands from host to receiver
  - inbound UBX replies from receiver to host
  - inbound RTCM3 frames generated by the base receiver
- So a non-ROS program must parse a mixed UBX + RTCM byte stream incrementally.

UBX frame format
- Sync: `0xB5 0x62`
- Then:
  - `class` : 1 byte
  - `id` : 1 byte
  - `payload_length` : 2 bytes, little-endian
  - `payload`
  - checksum `CK_A CK_B` : 2 bytes
- Checksum is the standard UBX 8-bit rolling checksum over:
  - `class`
  - `id`
  - `payload_length`
  - `payload`
- In other words, checksum covers the packet except sync bytes and except the checksum field itself.

UBX messages used by the current station code
- `UBX-MON-VER` poll:
  - class `0x0A`, id `0x04`
  - sent once after connect to identify the receiver
- `UBX-CFG-VALSET`:
  - class `0x06`, id `0x8A`
  - used to configure the station as fixed base
- `UBX-NAV-SAT` poll:
  - class `0x01`, id `0x35`
  - sent periodically for satellite count diagnostics
- `UBX-ACK-ACK`:
  - class `0x05`, id `0x01`
- `UBX-ACK-NAK`:
  - class `0x05`, id `0x00`

How poll requests are sent
- The code sends a normal UBX frame with the requested class/id and empty payload.
- Example categories:
  - poll `MON-VER`
  - poll `NAV-SAT`

ACK handling rule
- After sending the fixed-base `CFG-VALSET`, the code waits for:
  - `ACK-ACK` for `(class=0x06, id=0x8A)`, or
  - `ACK-NAK` for `(class=0x06, id=0x8A)`, or
  - incoming RTCM frames
- Practical rule in the current implementation:
  - if ACK arrives, trust it
  - if ACK does not arrive but RTCM starts flowing within the settle timeout, treat config as successful anyway
- This matters because the current receiver is noted to be unreliable about ACK on the fixed-base config transaction.

CFG-VALSET payload format used here
- Payload starts with 4 bytes:
  - version = `0x00`
  - layers
  - transaction
  - reserved = `0x00`
- Then repeated items:
  - `key_id` : 4 bytes, little-endian
  - `value` : encoded according to the key type
- Current code normally writes to RAM only:
  - layers = `0x01`
- If persistent config is requested, it adds:
  - BBR = `0x02`
  - FLASH = `0x04`

Exact configuration intent for the station receiver
- Enable UBX output on USB:
  - `CFG-USBOUTPROT-UBX = 1`
- Enable RTCM3 output on USB:
  - `CFG-USBOUTPROT-RTCM3X = 1`
- Disable NMEA output on USB in current YAML:
  - `CFG-USBOUTPROT-NMEA = 0`
- Set measurement rate:
  - `CFG-RATE-MEAS = 1000 ms` with current `measurement_rate_hz = 1.0`
  - code clamps to minimum `200 ms`
- Set navigation rate:
  - `CFG-RATE-NAV = 1`
- Set time reference:
  - `CFG-RATE-TIMEREF = GPS`
- Enable NAV-SAT reporting on USB:
  - `CFG-MSGOUT-UBX_NAV_SAT_USB = 1`
- Force time mode to fixed base:
  - `CFG-TMODE-MODE = 2` (`TMODE_FIXED`)
- Fixed position is LLH, not ECEF:
  - `CFG-TMODE-POS_TYPE = 1` (`TMODE_POS_LLH`)

How fixed coordinates are encoded
- Latitude coarse key:
  - `CFG-TMODE-LAT`
  - coarse scale: `1e-7 deg`
- Latitude high-precision key:
  - `CFG-TMODE-LAT_HP`
  - fine scale: `1e-9 deg`
- Longitude coarse key:
  - `CFG-TMODE-LON`
  - coarse scale: `1e-7 deg`
- Longitude high-precision key:
  - `CFG-TMODE-LON_HP`
  - fine scale: `1e-9 deg`
- Height coarse key:
  - `CFG-TMODE-HEIGHT`
  - coarse scale: `0.01 m`
- Height high-precision key:
  - `CFG-TMODE-HEIGHT_HP`
  - fine scale: `0.0001 m`
- Fixed position accuracy key:
  - `CFG-TMODE-FIXED_POS_ACC`
  - encoded as `position_accuracy_m * 10000`
  - unit is effectively `0.1 mm`

RTCM3 output configuration on the station
- Current code enables these RTCM message types on USB when using profile `msm4_low_bandwidth`:
  - `1005`
  - `1074`
  - `1084`
  - `1094`
  - `1124`
  - `1230`
- The corresponding UBX config keys are the `CFG-MSGOUT-RTCM_3X_*_USB` keys already mapped in `ubx.py`.

Important nuance about RTCM rates
- The code does not program per-message fractional RTCM output rates into the receiver.
- It only turns selected RTCM message types on or off in the receiver.
- Then it throttles outgoing frames in software after reading them from serial.
- Current logical profile is:
  - `1005` at `0.2 Hz`
  - `1074` at `1.0 Hz`
  - `1084` at `1.0 Hz`
  - `1094` at `1.0 Hz`
  - `1124` at `1.0 Hz`
  - `1230` at `0.2 Hz`
- If you want ROS-free behavior identical to this repo, implement the same software-side filter by RTCM message type.

RTCM3 frame format needed by the parser
- RTCM frames start with preamble `0xD3`.
- Length is a 10-bit value built from the next 2 bytes:
  - `payload_length = ((byte1 & 0x03) << 8) | byte2`
- Total frame size:
  - `3 + payload_length + 3`
  - header + payload + CRC24Q
- CRC is RTCM `CRC24Q` over all frame bytes except the final 3 CRC bytes.
- RTCM message type extraction used by the code:
  - `message_type = (frame[3] << 4) | (frame[4] >> 4)`

Mixed-stream parser behavior to keep
- Read arbitrary byte chunks from serial.
- Append them to a persistent buffer.
- Repeatedly do:
  - if buffer starts with `0xB5 0x62`, try parse UBX
  - else if buffer starts with `0xD3`, try parse RTCM
  - else discard bytes until next possible UBX sync or RTCM preamble
- On bad checksum or bad CRC, drop one byte and continue.
- This incremental behavior matters because sync bytes may arrive split across reads.

Station program sequence without ROS
1. Open the station USB serial port at `460800`.
2. Optionally send `UBX-MON-VER` poll and log the returned version strings.
3. Send one `UBX-CFG-VALSET` that:
   - enables UBX and RTCM3 output on USB
   - disables NMEA on USB if you want current repo behavior
   - sets `TMODE_FIXED`
   - writes the known LLH coordinates
   - enables the selected RTCM message types
4. Wait up to about `6 s` for either:
   - matching `ACK-ACK`, or
   - actual RTCM frames
5. Keep polling `UBX-NAV-SAT` about every `2 s` if you want satellite count diagnostics.
6. Continuously parse the mixed serial stream.
7. For each valid RTCM frame:
   - optionally inspect its message type
   - optionally apply the same software rate filter as this repo
   - forward the raw bytes unchanged toward the rover

Rover-side serial contract
- The rover correction input is just raw RTCM bytes.
- No JSON, no extra framing, no ROS serialization at the GNSS layer.
- The robot-side note explicitly says the existing rover node writes raw RTCM bytes to the rover receiver over USB.
- So a ROS-free rover helper can be as simple as:
  - open rover serial port
  - write each incoming RTCM frame byte-for-byte
  - flush as needed for low latency

What this repo does NOT define for the rover
- These files do not define a rover-side UBX configuration transaction.
- These files do not define the rover's final position output protocol.
- So from this repo alone, the guaranteed rover contract is only:
  - correction input over serial = raw RTCM3 frames
  - RTK fix computation happens inside the rover receiver itself
- If you also want to parse rover position in a non-ROS program, that part must follow the rover receiver's own configured output protocol, which is outside the station files reviewed here.

Practical bottom line
- The GNSS-specific protocol is simple:
  - configure the base with UBX
  - read RTCM3 from the same serial stream
  - send those RTCM3 bytes unchanged to the rover
- The most important implementation detail is not ROS; it is correct handling of the mixed UBX + RTCM serial stream and the fixed-base `CFG-VALSET` content.
